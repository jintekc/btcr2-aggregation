## The defect, stated precisely

### SC3, the string-seed wedge

`createRuntimeSettings` seeds the two free-text fields with a trim and nothing else, at
`runtime-settings.ts:467` and `runtime-settings.ts:473`. `applySettings` re-reads the STORED value
for every key a patch OMITS (`runtime-settings.ts:570` and `runtime-settings.ts:624`) and validates
it against `MAX_SERVICE_NAME_CHARS` (200) and `MAX_TERMS_CHARS` (20000). So an over-long seed does
not fail its own field. It fails every later save AS A SET, behind a sentence naming a field the
operator never touched, until the process restarts.

Reproduced by the verifier against the shipped module: a boot with a 5000 character `serviceName`
and a 100000 character `termsText` emits ZERO warnings and stores both at full length; a rename-only
save is then refused with `Participation terms must be 20000 characters or fewer.`, and a size-only
save with `Service name must be 200 characters or fewer.`.

Three things make this a blocking gap rather than a robustness note. `TERMS_TEXT` is the realistic
trigger, not a typo: 20000 characters is roughly 3500 words and SVC-05 exists precisely so an
operator can set a real participation-terms document. The wedge takes out capacity, threshold and
beacon type as well, which is the literal text of roadmap SC3 and the "without editing env vars or
restarting" clause of SVC-04. And the boot is silent, so nothing on screen or in the log explains
why the console stopped saving.

It shipped green because the block that claims to state the invariant as a property,
`expectHolderInvariants` at `runtime-settings.spec.ts:755`, checks numbers only, and `HOSTILE_SEEDS`
has no string row at all.

### W6, the warning that is not true

For a single `COHORT_TTL_MS=90000` boot the verifier observed two lines:

`[settings] discoveryWindowCeilingMs=90000 is not a whole number of minutes; using 60000 instead...`
then
`[settings] defaultDiscoveryWindowMs=90000 exceeds this service's cohort TTL; using 60000 instead...`

Both mislead. The cohort TTL IS 90000, so a window of 90000 does not exceed it: the clamp fired
against the already-quantized ceiling, not against the TTL, because 05-30 placed the window's
quantizer AFTER the clamp. And the operator set one variable, `COHORT_TTL_MS`, then was warned about
two others, one of which (`discoveryWindowCeilingMs`) appears in no environment reference, no compose
file and no ADR. `docs/DEPLOY.md:506` describes this case as producing one warning; it produces two,
and the second is false.

## The rule this plan holds

Stated once, because both halves collapse into it: **a boot value this service accepted without
complaint may never be a value it would later refuse, and every warning it does print must be true
of a variable the operator can act on.**
