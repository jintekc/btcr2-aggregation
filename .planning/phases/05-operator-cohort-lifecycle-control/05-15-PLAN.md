**Read the skeptics, not only the finder.** The finder's sighash taxonomy is wrong in a way that changes the fix:

- Only SIGHASH_NONE (0x02) and NONE|ANYONECANPAY (0x82) free the outputs and therefore enable change theft.
- SIGHASH_SINGLE variants (0x03, 0x83) DO commit to output 0 (the change output), so they do not enable change theft. They leave the OP_RETURN at vout 1 unbound, which silently destroys or substitutes the DID registration signal.
- ALL|ANYONECANPAY (0x81) commits to the outputs but lets an attacker append inputs.

All five non-default flavours are accepted today. Both skeptics therefore converged on the same fix shape: pin the ACCEPTED sighash set rather than blacklist one flag. This plan follows that shape.

**What the shipped SUMMARY claims, and why the executor should not trust it here.** `05-12-SUMMARY.md` presents the witness-free byte comparison as the complete anti-tampering argument, and `packages/web/src/lib/psbt.ts` says so in its own docstring ("A tampered input, output, amount, address or OP_RETURN payload all change those bytes, so all of them are caught by one comparison"). That claim is false for exactly one dimension: `unsignedTx` is `toBytes(false, false)`, the witness-free serialization, and the sighash flag lives in the PSBT field and in the witness, not in those bytes. The docstring is corrected by this plan.

<objective>
Stop a PSBT whose signature does not commit to this transaction's outputs from being validated as ok and handed to a broadcast call.

Purpose: on the wallet-signing path (D-21) the app never signs. Its whole job is the reverse of signing, and it is the only thing between an untrusted PSBT and a real broadcast. The template byte comparison is genuinely sound for structural tampering, but the sighash flag is the one dimension it cannot see, and a transport-level intermediary on the return leg is precisely the actor that check exists to stop. A signature made under SIGHASH_NONE commits to the input set and to no output at all, so any mempool observer can respend the same input with the same witness and redirect the change.

Output: one accepted-sighash gate beside the existing signature-presence check, one new refusal verdict with its own sentence, and a spec matrix that goes red against the current code.
</objective>

### Where the app's gate ends and the library's begins, stated so the matrix is not overstated

`@scure/btc-signer@1.8.1` validates the tapKeySig FIELD in its own PSBT coder: `SignatureSchnorr` throws "Schnorr signature should be 64 or 65 bytes long", and `tapKeySig` is wired to that coder. So a PSBT carrying a 63-byte or 66-byte signature cannot be parsed, and cannot even be constructed through `updateInput`, which runs the same coder. Two consequences the executor must respect:

- Through the public API, that input's honest outcome is the EXISTING unparseable verdict. A row asserting the new bad-sighash reason for it would stay red after a correct fix, and the only ways to make it green are to mock the parsed transaction (mocking the subject under test) or to loosen the assertion. Neither is acceptable, and both are the shape of the false greens this round exists to close.
- That public-API row may not be CONSTRUCTIBLE at all, and that is fine. `SignatureSchnorr` guards both `Transaction.fromPSBT` and `updateInput`, so a 63-byte or 66-byte tapKeySig has to be hand-spliced into the serialized bytes. If it cannot be, the row is DROPPED with the reason in the SUMMARY. What must not happen is a substitute: a generically corrupted PSBT returns `unparseable` for a reason that has nothing to do with signature length, so it would read as length coverage while pinning nothing. The predicate rows are the pin for that branch either way.
- The app's own default-refuse rule is therefore NOT reachable end to end. That is exactly why it is extracted into `isAcceptedTapKeySig` and asserted directly: the rule that a flavour nobody enumerated is refused by default is a real property, and it deserves a real pin, just not one that pretends to be an end-to-end path.

The five flag rows (0x02, 0x82, 0x83, 0x03, 0x81 refused; 64-byte and explicit 0x01 accepted) ARE genuinely end-to-end and genuinely red before the fix, because every one of those signatures is a valid 64 or 65 byte field the library parses happily.
