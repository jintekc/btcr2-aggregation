## The defect, and one thing the review and the verification both understated

Two independent boot values wedge the operator's only runtime configuration surface until restart.

**WR-2, integrality.** `numericKnob` validates finiteness and a lower bound but never integrality.
`applySettings` re-reads the STORED value for every key the patch omits and validates it with
`Number.isInteger`. So a fractional seed passes boot silently and then fails every later save AS A
SET, including a save of a field the operator did touch, behind a message naming a field they never
set. `createDraft` is hit the same way, because the draft's absent size is filled from the stored
default and `validateDraft` refuses it.

**WR-3, minute granularity.** A window that is integral but not a whole number of minutes is legal at
the knob and stores cleanly, then reaches the console as a fractional minutes field
(`msToMinutesText(90000)` is "1.5"), which `parseWindow` calls invalid because it mirrors the
server's own whole-minute guard. `SettingsView` validates the WHOLE form before it will post, so the
operator cannot save anything until they retype a field they never set. `DraftEditForm` is blocked
identically.

**What both accounts understate: no malformed env value is required.** `createService` fills these
seeds from other options when the `DEFAULT_*` ones are absent: the size seed from
`config.minParticipants`, the discovery-window seed from `cohortTtlMs`, the funding-window seed from
`fundingWindowMs`. Every one of those has its own env var with no whole-minute or integrality
constraint. So `COHORT_TTL_MS=90000`, which is a perfectly reasonable thing for an operator to set
and which nothing in the runbook warns against, wedges every settings save and every draft edit on a
service where no `DEFAULT_*` variable is set at all. `MIN_PARTICIPANTS=2.5` does the same through the
size seed. Verified by reading `createRuntimeSettings`'s call site in `packages/service/src/index.ts`
against the knobs `demo-server.ts` resolves.

That is the argument for fixing this at the HOLDER and nowhere else: it is the one place every seed
path meets, and a guard added at each env read would be several rules that can drift instead of one
that cannot. It also matches the precedent already in this file, where the discovery-window ceiling
clamp was deliberately placed at the holder rather than as a boot check in `demo-server.ts`, for the
same stated reason.

The documented default deploy path is unaffected: `docker-compose.yml` seeds `DEFAULT_SIZE=2` and
leaves the window seeds unset, and the built-in fallbacks are whole minutes. This is a robustness
gap, not a live defect on the shipped compose file, which is why it was a warning rather than a gap
and why it is third in this round.

## The rule this plan holds

Stated once, because both halves collapse into it: **no value this holder accepts may be a value it
would later refuse, and any window it will serve must round-trip through the console's minutes field
unchanged.**
