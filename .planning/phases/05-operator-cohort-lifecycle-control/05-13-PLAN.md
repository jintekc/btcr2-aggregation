## Phase Goal

Sourced from ROADMAP.md Phase 5, extended by the folded scoping one-pager `.planning/scoping/tos-payments-notifications.md`:

> The operator runs aggregation and manages a cohort's lifecycle, and, per the owner's decision to fold the three scoping one-pagers into this phase as build work, participants accept the service's terms with a DID-signed record when they join.

MVP slice framing: **As a** service operator with terms my participants should agree to, **I want to** have their acceptance recorded as something signed and provable, **so that** agreement is a fact I can point to rather than a claim I make.

This is the third and last of the SLIP-FIRST folded builds (D-22), and it is deliberately bounded: payments, notifications, and contracts are NOT built here. They stay requirements capture for the next milestone, because the anonymous-utility versus accounts product-model decision comes first. It introduces requirement SVC-05, minted at planning time following the LIVE-01 precedent. Its operator half (the terms text setting) shipped in 05-07.

## Artifacts this phase produces (Phase 5, cumulative - excludes these from drift verification)

See the cumulative list in `05-01-PLAN.md`. This plan creates: `packages/shared/src/tos.ts` with `TermsAcceptance`, `buildTermsAcceptance`, and `termsHashHex`; the acceptance artifact kind in `packages/service/src/store.ts`; route `POST /v1/terms/acceptance`; `TermsStep` (packages/web/src/components/browse/TermsStep.tsx); the specs `packages/shared/tests/tos.spec.ts`, `packages/service/tests/tos.spec.ts`, and `packages/web/tests/terms.spec.ts`; and requirement id `SVC-05`.

<objective>
Record a participant's agreement to this service's terms as a DID-signed, server-verified, hash-bound artifact, using only machinery this app already owns.

Purpose: both sides already hold did:btcr2 identities and signing keys, which makes a signed acceptance the lowest-new-trust path available, and the app already has a canonical hashing helper, the participant's key in the browser, and a content-addressed store with a hash-addressed public read. Three things decide whether the result is a proof or theatre. The record must bind the HASH of the terms shown, so editing the terms later cannot change what an old acceptance means. The signature must be verified server-side, because an unverified stored blob proves nothing. And the format must be frozen by a pin, because once real acceptances exist participants may rely on it.

Output: the canonical record and its hash in shared, server-side verification and hash-addressed storage, a public acceptance route, the join-flow terms step with escaped rendering, and three specs.

Slip tier (D-22): SLIP-FIRST. This is one of the three folded scoping one-pagers (05-11, 05-12 and 05-13); if the phase runs long it re-parks cleanly to Phase 6 or the next milestone, and no CORE-tier plan (05-01 through 05-07 and 05-10) depends on it.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous participant -> public acceptance route | An unauthenticated caller can submit records for storage. |
| operator-authored terms text -> participant browser | Long operator text is rendered to strangers. |
| stored acceptance -> anyone with its hash | The artifact store's read is unauthenticated and hash-addressed. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-13-01 | Spoofing | an acceptance forged for another participant's DID | high | mitigate | The signature is verified server-side against the key resolved from the claimed DID using the same resolution the transport already uses for envelope authentication; an unverified record is never stored. |
| T-05-13-02 | Tampering | a terms edit changing the meaning of a stored acceptance | high | mitigate | The record binds the HASH of the terms shown, not the text, and the stored artifact is content-addressed and never rewritten; the spec pins that a later edit leaves an existing acceptance byte-unchanged. |
| T-05-13-03 | Tampering | stored cross-site scripting via terms text | high | mitigate | Terms text renders as plain auto-escaped React text content only, inside a scroll-capped container, with no dangerous HTML prop anywhere in the web source and a server-side length bound from 05-07. |
| T-05-13-04 | Denial of Service | unauthenticated writes to the artifact store | medium | mitigate | The route refuses before storing anything unless the service has terms set, the submitted hash matches the current terms, and the signature verifies; the body carries the established size limit, so an unverified caller cannot grow the store. |
| T-05-13-05 | Information Disclosure | an acceptance record readable by hash | medium | accept | The record is a public statement by design (it is the proof the participant agreed) and is unguessable without its hash. It is served only by the existing hash-addressed read, appears on no listing endpoint, and its reference is shown only to the accepting participant and to the operator. |
| T-05-13-06 | Information Disclosure | the acceptance route as an existence oracle | medium | mitigate | Every refusal returns the same caller-facing shape while the real reason is logged server-side, so the route cannot be used to probe which DIDs or cohorts this service has seen. |
</threat_model>
