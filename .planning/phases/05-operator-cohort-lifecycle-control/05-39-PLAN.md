## The defects, stated precisely

### CR-03: a probe can end a session without ending it

`sessionRound`'s docstring (`packages/web/src/stores/operator.ts:349-377`) states the rule the three
guards 05-36 landed lean on: a round is "bumped on every path that makes a session LIVE ... and on
every path that ENDS one (`signOut`, `expireSession`)".

There is a third path that ends one, and it is inside `probe`. `OperatorConsole` is mounted
conditionally on the operator tab (`App.tsx`), so switching away and back re-runs `probe`
(`OperatorConsole.tsx:43-45`). If the session cookie expired while the operator was on the
participant tab, where nothing polls and so no 401 is ever seen, the probe is what discovers it, and
the discovery does nothing except set a status string (`operator.ts:813-817`). The transport-fault
branch (`:818-822`) retains everything too. `signIn` clears none of it (`:825-844`), so the next
session inherits the whole gated slice.

Four consequences, in order of how long they last:

1. **The settings snapshot never refreshes.** `OperatorConsole.tsx:65-69` re-reads settings only
   while the snapshot is `undefined`. It is defined, so the latch never fires and the create form
   opens on a previous session's defaults indefinitely, until the operator happens to open the
   Settings view. This is the exact harm WR-09's fix cites as its reason for existing, reached with
   no race at all.
2. **The health strip renders a previous session's broadcast mode.** If the service was restarted
   between the two sessions, which is the ordinary reason a cookie stops being accepted, the mode
   chip is a claim about whether this service can move Bitcoin, carried over from a boot that is
   gone.
3. **The drill-down opens straight onto the dead session's document.** `view` is not reset, so
   session B mounts `CohortDetail` on session A's members, pubkeys, signed updates and funding view,
   with a `lastUpdated` stamp session B never earned.
4. **An in-flight read issued by the dead session still writes**, because the round it captured still
   matches.

This fails CLOSED against the service (every route still refuses the dead cookie), so it is not an
authentication weakness. It is the console asserting facts about a session that no longer exists, on
the surface whose own copy promises the opposite ("Monitoring rebuilds from this service's state
after you sign in"), plus one wrong value that persists rather than self-healing.

### WR-11: the transition is decided from a snapshot a second probe erases

`probe`'s first statement takes `auth` away from `logged-in`, so 05-36 captured `wasLive` before it
(`:790-796`). That is correct for one probe and wrong for two: a second probe entering while the
first is in flight reads `checking`, concludes no session was live, and bumps the round when it
lands. `main.tsx:6-10` enables React StrictMode, which double-invokes mount effects in development,
so this fires on every console mount in dev; in a production build a fast tab toggle does it.

The cost today is one discarded list read. What it costs after CR-03 is worse, and this is why the
two findings are one plan: once `probe` ENDS sessions, two overlapping probes would both call the
end-of-session operation, and the second would land the session-expired copy on a console that has
already moved on.

### IN-11: two clear lists for one act

`signOut` (`:846-907`) clears `createStatus`, `formError`, `advertiseStatus`, `advertisingId` and
`advertiseMessage`; `expireSession` (`:909-949`) clears none of the five. A `formError` from a failed
advertise or a green `advertiseMessage` from a successful one therefore survives an expiry and
renders on the next session's create form and cohort list. Both surfaces are hidden while logged out,
which is why the review files it as info; it becomes the vehicle for WR-12's stale copy, and it is
the foundation CR-03's one-operation fix builds on.

## The rule this plan holds

**Ending a session is one act with one implementation, decided from a stored fact rather than from a
status, and it clears one set of state defined in one place. A path that discovers a session has
ended and only writes a status string has not ended it.**

## Why a stored live-session fact, and not probe dedupe

The review offers two fixes for WR-11: dedupe the in-flight probe, or record the live session
explicitly. This plan records it explicitly, and the reason is a case dedupe does not cover.

Dedupe removes the second probe but leaves the decision on a status captured before the probe's own
first assignment. Consider a deliberate sign-out landing while a single probe is in flight: the
snapshot says a session was live, `signOut` ends it, the probe lands `logged-out`, and the fix would
call the end-of-session operation again, telling the operator their session EXPIRED about a session
they themselves just ended. A stored fact read at landing time has already been cleared by
`signOut`, so the probe correctly does nothing. Dedupe would also key an identity on request timing
and would carry an unstated assumption that every caller passes the same base URL.

The cost of the stored fact is that three `setState` seed helpers in the spec have to seed it, which
is a real footgun and is closed the way this phase has closed footguns before: a row pins that a
seeded live console carries the same session-identity fields a real `signIn` produces, so a seed
that forgets fails rather than passes quietly.
