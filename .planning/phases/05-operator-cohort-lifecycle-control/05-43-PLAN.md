## The defects, stated precisely

### WR-14: a sixteenth gated call site, rendering an authentication denial as form validation

`UpdateDraftResult` (`packages/web/src/lib/operator.ts:198-211`) carries an `unauthorized` member and
its docstring says why: an edit is reachable from a console the operator may have left open past
their session, so a 401 must take the one honest re-login path rather than being rendered as a
validation failure. Every word of that is equally true of create. `CreateDraftResult` (`:168`) has
only `ok: true` and `ok: false` with a string, so `createDraft` (`:175-196`) treats a 401 like a 400
and lifts the body's error verbatim.

The reviewer reproduced it: after a 401 create the console reads `auth = logged-in`,
`createStatus = error`, and the form error slot holds the service's own generic denial string from
`packages/service/src/operator-auth.ts:169`, rendered at
`packages/web/src/components/operator/CreateCohortForm.tsx:123`. That string is not UI-SPEC copy, it
names no field, and it appears where `Cohort size must be at least 1 signer.` otherwise appears. The
session is not ended and the round is not retired, so D-16's rule that a 401 never means two
different things does not hold for the create verb.

The blast radius is bounded: the create form renders only on the list view, where the console polls
every 4000 ms, so `refreshCohorts` expires the session within a tick and (since 05-39) the reset
clears `formError` with it. What remains is up to one poll interval of an internal auth string
presented as form validation, plus one gated call site the enumeration silently excludes, so a
reader checking the claim against the file cannot tell the omission from a decision.

### WR-15: a 502 now narrates an expiry the service never claimed

`sessionProbe` (`packages/web/src/lib/operator.ts:50-63`) maps 200 to `logged-in`, 404 to `disabled`,
and everything else to `logged-out`. A 500, a 502 from a reverse proxy mid-reload, or a 503 from a
load balancer is therefore indistinguishable from a 401 by the time the store sees it. Before round 7
that mattered little: the branch set a status. Now it calls `expireSession()`, which retires the
round, writes the session-expired sentence and clears the entire gated slice.

The reviewer reproduced it: after a 502 probe, `auth = logged-out`, the error line is the
session-expired copy, and `cohorts`, `health`, `settings` and the drill-down are all gone. Four lines
below, the `catch` branch makes precisely the opposite decision on the same class of event and says
so in its comment. `fetchCohortDetail` (`:564-568`) states the same rule for the same statuses: a
non-401 non-ok is a transient fault, not a session change, so freeze the last-known view rather than
logging the operator out (D-25).

The harm is a false claim in the console's most load-bearing sentence, plus the loss of the frozen
last-known state D-25 exists to preserve, on the one path an operator meets after a service hiccup.

### IN-15: a phantom session for one tick

The trio's docstring names `probe`'s session-ENDED branches as the ONE documented exception. The
session-STARTED branch (`packages/web/src/stores/operator.ts:976-995`) is exempt too and is not
named: it decides only from `liveSessionRound` read at landing time, which cannot distinguish
`nobody was ever signed in` from `a session ended one millisecond ago`.

The reviewer reproduced it with a list read and a probe in flight together, the read answering 401
first: after the 401 the console is correctly logged out on a retired round, and after the probe it
re-enters a signed-in shell for a cookie the service has already refused, still carrying the expiry
copy in `error`. It self-heals on the phantom session's own first read, so the visible cost is a
flicker and the interleaving needed is narrow. It is recorded because the exemption taken is wider
than the exemption written down.

## The rule this plan holds

**A 401 is the only answer that ends a session, it ends one everywhere it can be answered, and it
never renders as anything else. Every other unhappy answer freezes rather than claims.**

## Why widen the probe's vocabulary rather than special-case the store

The store cannot recover a distinction the client function already collapsed. `sessionProbe` returns
one value for two different facts, so any repair inside `probe` would be guessing. The shipped
precedent for the fix is one file away: `fetchCohortDetail` returns a discriminated result whose
`unreachable` member exists precisely so the store can tell a session change from a transient fault,
and every other read in this codebase already draws the line there. This makes the probe read like
its three siblings rather than like an exception.

Widening `SessionState` also makes the compiler do the enumeration: once `unreachable` is a member,
the store's own assignment of a probe answer to the console's auth posture stops type-checking until
every case is handled, so `pnpm --filter @btcr2-aggregation/web exec tsc --noEmit` is the first proof
that no case was missed.
