## Gap source

This plan closes **audit defect 7** from `.planning/phases/05-operator-cohort-lifecycle-control/05-AUDIT.md` (entry 9, MEDIUM, honesty), filed as `.planning/todos/pending/2026-07-29-reserve-the-anchored-chip-for-confirmed-anchors.md`.

**Read the skeptics, not only the finder: the framing changes materially.** The finder framed this as a kill-switch consequence (a stood-down cohort publishes nothing yet reads as Anchored). Skeptic 2 reproduced that AND reproduced a second, broader case with no kill switch involved: on the mainline live path, a beacon transaction that was broadcast but did not confirm inside the confirm window also reads as Anchored, because a `beacon-anchored` frame carrying an unconfirmed flag is deliberately ignored. That case has no health-strip cue at all and is arguably the more consequential one. A third case follows from the same code: on the default hermetic path every completed fixture cohort reads as Anchored too.

So the defect is that `signing-complete` mints an on-chain claim in EVERY mode, and confirmation was never a precondition for the list chip or the counter. It most likely predates Phase 5 and arrived with the Phase 4 monitor (04-02).

### Scoping decision: this belongs in THIS gap round, not a Phase 4 revisit

The todo suggests triaging it against 04-02. This plan deliberately does not do that. The reasoning, recorded so it is not re-litigated:

- **A Phase 4 revisit has no home.** Phase 4 is complete, verified and closed. Deferring a confirmed defect to a finished phase means deferring it indefinitely, which is the failure mode this project's course-correction exists to avoid.
- **The owner is about to walk `05-UAT.md`.** The audit separately flags that `05-UAT-CHECKLIST.md` instructs the owner to confirm a hermetic cohort ends with the good-tone Anchored chip. Left alone, the human pass blesses the defect. Fixing the checklist without fixing the chip would be worse.
- **It contradicts a written contract, not a preference.** `04-UI-SPEC.md` defines the list chip as reserved for a confirmed beacon transaction. The drill-down timeline honors that rule and says so in its own source; the list chip and the counter do not.
- **The fix is contained and both skeptics converged on the same shape**, so there is no design risk to resolve first.

It is scheduled LAST in the round (wave 4) because it is the lowest-severity of the four service-side defects, it is the one most likely to ripple into pins, and every real-funds fix must be committed before it starts.

### Reversibility

Rated **costly**, not one-way, so no decision checkpoint is inserted. A chip taxonomy is pinned by the served DTO, by unit specs, by two end-to-end legs, by the UI-SPEC tone map and by the UAT checklist, so it must migrate all of them in one change (the same posture 05-CONTEXT D-07 recorded for the additive status bit). It is fully revertible in code: nothing is persisted and no participant-facing surface carries the chip.

**TWO consequences the executor must state plainly in the SUMMARY, because both are user-visible.**

1. On the default hermetic path the anchored counter will read zero permanently and every completed cohort will appear as a co-signed row in the Ended group. That is the honest reading (a hermetic service anchors nothing), and it is where an operator counts completions. The metrics row gains no replacement column in this plan: see the prohibition and the follow-up note.

2. **The list-level fallback signal is given up on every path where no confirmation arrives, and this plan chooses that deliberately rather than by omission.** After the change, `'fallback'` is minted ONLY inside the confirmation-gated `beacon-anchored` handler. So on the hermetic default (no broadcaster, which is what `pnpm e2e:fallback:operator` and the shipped `packages/service/tests/monitor.spec.ts` row titled for a k-of-n script-path completion both drive) and on the broadcast-but-never-confirmed path, a script-path co-sign now reads `co-signed`. Because `groupForChip('fallback')` is the only thing that put such a row in Needs attention, that bucketing goes with it: the row lands in Ended. Every existing assertion would stay green through this (the `fallback` chip still exists as a type, and the monitor spec row simply gets migrated), which is exactly why it is called out here rather than left for the next audit to find.

**Why the loss is accepted rather than closed, and what bounds it.** Minting `'fallback'` at co-sign time is not an option: `'fallback'` is itself an anchored claim (its own docstring reads "anchored via the k-of-n script path" and it counts toward the anchored metric), so keeping it at `signing-complete` would preserve the very lie this plan exists to remove for script-path cohorts. The alternative that would close the loss is to carry the retained fallback tag into the summary DTO so an unpromoted script-path row renders a distinct label or flag. That is a served-DTO widening plus a rendering change in a package with no DOM harness, in a gap round with two real-funds fixes in flight, so it is recorded as a follow-up instead (see the follow-up note in verification) rather than taken here.

What bounds the loss are two assertions in this plan that go red if it widens: the drill-down's `fallback.used` stays true for a hermetic script-path cohort, and one operator-rows row pins where an unpromoted script-path row now groups alongside the still-true `groupForChip('fallback') === 'attention'`. The consequence also goes into `05-UAT-CHECKLIST.md` beside the anchored-counter note, so the owner walking the checklist reads it rather than inferring it.

<objective>
Stop the co-sign completing from minting a claim about Bitcoin.

Purpose: the operator console has one rule about this word, written in its own source and in the Phase 4 UI spec: Anchored is reserved for a confirmed anchor. The drill-down obeys it. The list chip and the metrics row do not, because both are derived from a `signing-complete` record that knows nothing about the chain. The result is a good-tone Anchored badge and an incremented anchored counter for three distinct situations in which nothing was confirmed, one of which mixes genuinely confirmed cohorts and never-published ones in one list under one identical chip with no per-cohort way to tell them apart.

Output: an honest intermediate terminal fate, a promotion that happens only on a confirmed frame, a counter that only ever reports confirmed anchors, and every pin migrated in the same change.
</objective>
