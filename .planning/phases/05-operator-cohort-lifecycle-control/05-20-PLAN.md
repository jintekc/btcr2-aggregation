## Gap source

This plan closes **audit defect 7** from `.planning/phases/05-operator-cohort-lifecycle-control/05-AUDIT.md` (entry 9, MEDIUM, honesty), filed as `.planning/todos/pending/2026-07-29-reserve-the-anchored-chip-for-confirmed-anchors.md`.

**Read the skeptics, not only the finder: the framing changes materially.** The finder framed this as a kill-switch consequence (a stood-down cohort publishes nothing yet reads as Anchored). Skeptic 2 reproduced that AND reproduced a second, broader case with no kill switch involved: on the mainline live path, a beacon transaction that was broadcast but did not confirm inside the confirm window also reads as Anchored, because a `beacon-anchored` frame carrying an unconfirmed flag is deliberately ignored. That case has no health-strip cue at all and is arguably the more consequential one. A third case follows from the same code: on the default hermetic path every completed fixture cohort reads as Anchored too.

So the defect is that `signing-complete` mints an on-chain claim in EVERY mode, and confirmation was never a precondition for the list chip or the counter. It most likely predates Phase 5 and arrived with the Phase 4 monitor (04-02).

### Scoping decision: this belongs in THIS gap round, not a Phase 4 revisit

The todo suggests triaging it against 04-02. This plan deliberately does not do that. The reasoning, recorded so it is not re-litigated:

- **A Phase 4 revisit has no home.** Phase 4 is complete, verified and closed. Deferring a confirmed defect to a finished phase means deferring it indefinitely, which is the failure mode this project's course-correction exists to avoid.
- **The owner is about to walk `05-UAT.md`.** The audit separately flags that `05-UAT-CHECKLIST.md` instructs the owner to confirm a hermetic cohort ends with the good-tone Anchored chip. Left alone, the human pass blesses the defect. Fixing the checklist without fixing the chip would be worse.
- **It contradicts a written contract, not a preference.** `04-UI-SPEC.md` defines the list chip as reserved for a confirmed beacon transaction. The drill-down timeline honors that rule and says so in its own source; the list chip and the counter do not.
- **The fix is contained and both skeptics converged on the same shape**, so there is no design risk to resolve first.

It is scheduled LAST in the round (wave 4) because it is the lowest-severity of the four service-side defects, it is the one most likely to ripple into pins, and every real-funds fix must be committed before it starts.

### Reversibility

Rated **costly**, not one-way, so no decision checkpoint is inserted. A chip taxonomy is pinned by the served DTO, by unit specs, by two end-to-end legs, by the UI-SPEC tone map and by the UAT checklist, so it must migrate all of them in one change (the same posture 05-CONTEXT D-07 recorded for the additive status bit). It is fully revertible in code: nothing is persisted and no participant-facing surface carries the chip.

**ONE consequence the executor must state plainly in the SUMMARY, because it is user-visible.**

On the default hermetic path the anchored counter will read zero permanently and every completed cohort will appear as an unconfirmed co-sign row in the Ended group (or, for a script-path cohort, under Needs attention as it does today). That is the honest reading (a hermetic service anchors nothing), and it is where an operator counts completions. The metrics row gains no replacement column in this plan: see the prohibition and the follow-up note.

### The list-level fallback signal is KEPT, and here is the shape that keeps it

An earlier draft of this plan gave up the list-level `fallback` chip and its Needs-attention bucketing on every unconfirmed path, including the shipped hermetic default, and documented that as an accepted loss. **That is no longer the plan, and a reviewer was right to push back on it: it was a default-path product regression taken inside a defect-closure round, and it turned out to be avoidable at almost no cost.**

The reasoning that led to the loss was sound as far as it went. Minting `'fallback'` at co-sign time is NOT an option: `'fallback'` is itself an anchored claim (its own docstring reads "anchored via the k-of-n script path" and it counts toward the anchored metric), so keeping it at `signing-complete` would preserve the very lie this plan exists to remove, for exactly the cohorts that took the script path. What the earlier draft then assumed was that the only alternative was a served-DTO widening plus a rendering change: carry the retained fallback tag into the summary DTO as a separate field and have the component render a flag beside the chip.

There is a third option, and it is strictly smaller than either: **mint a SECOND unconfirmed chip.** This plan already widens the `CohortChip` union and already moves the chip presentation into an exported, spec-readable accessor. Adding one more union member costs one more entry in a record the type checker already forces to be exhaustive, one more `groupForChip` answer, and one more row in the presentation spec. No DTO field is added, no consumer signature changes, and nothing needs a DOM harness, because Task 2's whole point is that tone, label and grouping become assertable from a lib module.

The taxonomy is then a clean two-by-two, and every quadrant says only what the service actually knows:

| | key path | k-of-n script path |
|---|---|---|
| **confirmed on-chain** | `anchored` (good tone, counts anchored) | `fallback` (warn tone, counts anchored) |
| **not confirmed** | `co-signed` (neutral, counts neither, Ended) | `co-signed-fallback` (warn, counts neither, Needs attention) |

So on the hermetic default (no broadcaster, which is what `pnpm e2e:fallback:operator` and the shipped `packages/service/tests/monitor.spec.ts` row titled for a k-of-n script-path completion both drive) and on the broadcast-but-never-confirmed path, a script-path co-sign reads `co-signed-fallback`, stays in Needs attention, and no longer claims an anchor. The operator loses nothing they have today; the console stops asserting a fact about Bitcoin that it does not have. The honest-labelling half of the defect closure and the existing product signal are both kept.

**What is still pinned as a boundary.** Two assertions go red if the distinction erodes anyway: the drill-down's `fallback.used` stays true for a hermetic script-path cohort (untouched derivation), and ONE operator-rows row pins all four terminal groupings together, so a future change that quietly routes `co-signed-fallback` into Ended (which is what "simplify the two unconfirmed chips into one" would do) turns it red. The shipped k-of-n monitor row migrates to `co-signed-fallback` with `anchored: 0` and NOT to plain `co-signed`; that migration target is a prohibition, because migrating it to `co-signed` is precisely how the regression would come back with a green suite.

**Cost of the second chip, stated so it is not a hidden trade.** The list taxonomy grows from eight chips to ten (`draft`, `filling`, `co-signing`, `needs-funding`, `co-signed`, `co-signed-fallback`, `fallback`, `anchored`, `failed`, `expired`, `canceled` minus the two client-only ones already counted). That is more surface for a reader to learn, and it is why the label-distinctness row runs over the WHOLE chip set rather than over the new entries. The Phase 4 UI-SPEC tone map is NOT amended: it is a closed-phase artifact, and after Task 2 the exported `CHIP_PRESENTATION` in `packages/web/src/lib/operator-rows.ts` is the single live definition of every chip's tone, label and pulse, which is a better home for it than a historical spec. Say that in the SUMMARY so nobody reads the unamended Phase 4 spec as drift.

</objective>
