## The structural decision, and why

The audit names two structural causes. Both are fixed here, and the DOM decision needs justifying
because the round brief scoped two candidates that this plan does not take.

**Cause 2, typechecking, is unambiguous.** The root `tsconfig.json` references shared, service,
participant and e2e only, so `pnpm test` (`tsc -b && vitest run`) never typechecks `packages/web`.
Worse, `packages/web/tsconfig.json` has `include: ["src"]`, so `packages/web/tests` is typechecked by
NOTHING at all, not even `pnpm --filter @btcr2-aggregation/web build`. Fourteen spec files sit
outside every type gate in the repo.

**Cause 1, the DOM.** The brief scoped per-file `// @vitest-environment jsdom` docblocks versus a
root `vitest.workspace.ts`. Both presuppose installing jsdom or happy-dom. This plan takes a third
option and states the reasoning:

- `react-dom/server`'s `renderToStaticMarkup` renders real components in the EXISTING `node`
  environment. Verified on this checkout against `ConfirmPanel`, `HealthStrip` and `ServiceControls`.
- It adds ZERO packages. jsdom would be a new, unaudited dependency; this repo's package-legitimacy
  gate would require a blocking human checkpoint before installing it, which conflicts with this
  round's autonomous contract. Nothing is installed, so no legitimacy row and no checkpoint arise.
- It changes NOTHING about test discovery. A `vitest.workspace.ts` would restructure how all 1049
  tests are found, for no benefit unless jsdom is adopted.
- Every render-gated defect in the audit is an INITIAL-render fact: a prop not passed, a label not
  asserted, a guard not rendered, a `useState` initializer not seeded. `useState` initializers DO
  run during a static render, which is why this approach closes `#31` (`DraftEditForm` seeding)
  without a source refactor.

**How state reaches a static render, stated precisely because the obvious answer is WRONG.** A first
version of this plan claimed a store seeded with `setState` renders what the browser renders. That is
false, and the correction is the most important sentence in this file.
`node_modules/.pnpm/zustand@5.0.14_.../zustand/esm/react.mjs` passes THREE arguments to
`useSyncExternalStore`, and the third, the SERVER snapshot, reads `api.getInitialState()`, not
`api.getState()`. `renderToStaticMarkup` always takes the server snapshot. So a static render sees
the state the store was CREATED with, and every `setState` before it is invisible. Verified directly:
a store created at 1 and set to 42 renders 1.

That failure mode is silent and it produces VACUOUS GREENS, which is the exact shape of defect this
round exists to close. Four rows asserting that an empty terms body renders nothing would all pass
against an unseeded store no matter what the component does. So this plan forbids `setState` seeding
for renders outright, and uses two seeding modes instead:

1. **Preferred: render the pure-prop component.** Where the branch under test lives in a component
   whose inputs are props, render that component directly. `CancelConfirm`, `TestPeerAction` and
   `DraftEditForm`'s seeding block are all in this class, and reaching them costs one `export`
   keyword. No fake, no store, nothing to get wrong.
2. **Where the state is only reachable through a module-singleton store**, install a
   SELECTOR-FAITHFUL FAKE of the bound hook with `vi.mock` plus `importOriginal`, replacing ONLY the
   hook and keeping every other export of that module real. The fake is
   `(selector) => selector(fixture)` with a `getState` reading the same fixture, and it must read the
   fixture LAZILY at call time so a per-row assignment is visible. `HealthStrip`, `ServiceControls`,
   `TermsStep`, `LifecycleActions` and `CohortRow` are in this class.

Mode 2 replaces the store CONTAINER, never the component's own selectors: each
`useOperator((s) => s.health?.mode)` in the component still executes, against the fixture. So a
component that reads the wrong field, or stops reading one, still fails. That is what keeps mode 2
from being a stub of the subject. Verified on this checkout: with the fake seeded to a live mode,
`HealthStrip` rendered the live label; with the real store and `setState`, it rendered the
pre-first-read fallback.

**Every render describe block carries an anti-vacuity control.** At least one row per block must
assert that a DIFFERENT fixture produces DIFFERENT output. A block whose rows all assert an absence
proves nothing until one row proves the fixture reaches the renderer at all.

**The honest limit, stated in the helper and in the SUMMARY.** A static render fires no events, runs
no effects, performs no state transitions, and reads a store's initial state rather than its current
one. Where a defect genuinely needs interaction, the assertion is taken against the inner component
the interaction reveals (this plan exports `CancelConfirm` for exactly that reason), or it is left to
the real-Chromium playwright-core legs the repo already has. That is the same split the audit itself
proposes for #27. If a DOM environment is ever adopted, what it would ADD is interaction and a live
store: clicking `Cancel cohort` and watching the panel arm, rather than rendering the panel the click
reveals. That is worth recording, and it is not worth a new dependency today.
