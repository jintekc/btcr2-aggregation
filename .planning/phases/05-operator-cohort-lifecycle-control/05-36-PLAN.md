## The defect, stated precisely

### IN-07: a round identifies a probe EVENT, not a session

`sessionRound`'s docstring (`packages/web/src/stores/operator.ts:349-369`) states the field's meaning
as law: "a round identifies exactly one session, live or ended", and "any guard that must decide
whether an answer still belongs to the session that asked compares this, never `auth` alone".

`probe` (`:781-800`) bumps on every landing of `logged-in`, including when the SAME session is
already live. `OperatorConsole` is mounted conditionally on the operator tab (`App.tsx:112-117`), so
every switch away and back re-runs `probe`, retires the live session's round, and discards any list
read in flight across the switch. The cost today is one skipped update, recovered 4000 ms later. The
reason it matters is that this plan adds three more guards that compare this field, and a field
whose stated subject and actual subject differ is a guard nobody can reason about.

There is a mechanical trap in the fix: `probe` sets `auth: 'checking'` as its FIRST statement, so by
the time the probe's answer lands, `get().auth` is never `logged-in` and a naive transition check
would bump on every probe exactly as today. The status the transition is measured against has to be
captured BEFORE that first `set`.

### WR-08: a stale 401 from an ended session signs the NEXT session out

`refreshCohorts` (`:928-1003`) captures `askedInRound` before its await and compares it in the ok
path (`:975`), which is what 05-34 landed for WR-06. Its 401 branch (`:942-952`) calls
`expireSession()` with no comparison at all, and the comment defending that order (`:946-949`)
claims "both are session-scoped, so neither order changes what happens". The second clause is false,
and false for exactly the reason WR-06 was real: a 401 is evidence about the ASKING session, and the
two branches are scoped to DIFFERENT sessions.

The sequence needs no unusual timing, and the store's own comment supplies the premise: the console
polls every 4000 ms against an 8000 ms timeout, so two reads are routinely outstanding. When the
session expires server-side both answer 401. The first is correct and expires the session. The
operator signs straight back in. The second 401, issued by the session that already died, expires
the new one. The reviewer reproduced it against the shipped store with no source modified.

What the operator sees: they sign in, the console paints, and within a second or two it throws them
back to the login screen claiming their session ended, about a session whose cookie this service
would still accept. `expireSession` clears the whole gated slice on the way out, so an open
drill-down, an unsaved draft edit and the settings snapshot go with it. It fails CLOSED, so this is
not an authentication weakness; it is a false statement to the operator plus lost console state on
the console's least forgiving screen.

The identical unguarded shape is at `pollDetail` (`:1359-1368`), `loadSettings` (`:1277-1281`) and
`saveSettings` (`:1310-1313`).

### WR-09: the rule was applied to one of three gated reads

`pollDetail` (`:1348-1387`) guards on the cohort id and nothing else, so the ABA sequence survives
whenever the operator reopens the cohort they were already watching. That slot is not a summary: it
carries member DIDs and pubkeys, raw signed updates, co-sign progress, the funding view (beacon
address, recovery-key state, the mainnet real-money lines) and the activity ring, plus a
`lastUpdated` stamp the new session never earned and the drill-down renders as its freshness clock.

`loadSettings` (`:1275-1289`) has no session guard of any kind on either branch, and its write is
not transient: `OperatorConsole.tsx:65-69` re-reads settings only while the snapshot is `undefined`,
so a dead session's answer landing in the gap makes the new session skip its own read entirely. The
new operator then creates cohorts from the previous session's defaults
(`CreateCohortForm.tsx:32-45,94-102`) and, until they happen to open Settings, never sees a value
this service reported to them. Round 5 also widened what that slice carries: `droppedSeeds` is boot
provenance about the operator's own environment and now crosses the same boundary.

`saveSettings` (`:1291-1320`) has the same shape on all three of its branches.

## The rule this plan holds

**An answer is evidence about the question that was asked, and the question was asked by ONE
session. Every gated read compares the asking session before it writes anything and before it acts
on a refusal, on every branch, because a 401 is as much a fact about the asker as an ok body is.**
