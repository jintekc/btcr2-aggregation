## The defect, stated precisely

05-32 added the round guard the round-3 report asked for, and it closes the case that report
reproduced (a fast 401 and a slow ok, settled in that order). It does not close the case its own
comment claims.

At `packages/web/src/stores/operator.ts:899` the pre-await capture is
`const askedWhileLive = get().auth === 'logged-in'`, a boolean derived from a STATUS. At lines 926
through 928 the post-await re-check compares that same status again. Both halves therefore ask "is
some session live", never "is it the SAME session". `logged-in` to `logged-out` to `logged-in` is
ABA: the string is identical, the session is not, and nothing in the store carries a session
identity or a round counter for the comparison to use.

Compare the precedent the guard's own comment cites. `pollDetail` captures `askedFor = view.cohortId`
at line 1308 and compares `current.cohortId !== askedFor` at lines 1326 through 1329. That is an
IDENTITY comparison, which is why that guard is sound. Round 4 copied the shape and not the subject.

The reviewer reproduced the consequence against the shipped store, with no source modified: after an
expiry cleared everything, a re-sign-in followed by the previous session's read landing left
`auth: logged-in` alongside one cohort, a served health object claiming `mode: live` and
`esploraReachable: true`, a populated metrics object, and `lastUpdated` set.

The window is the ordinary one the fix's own comment describes: `OperatorConsole.tsx:13` polls every
4000 ms and `packages/web/src/lib/operator.ts:12` gives each read an 8000 ms timeout. The sequence is
a session expiry, an operator signing straight back in (a password-manager fill is a second or two),
and the previous session's read landing into the new one. The new session then renders the old
session's cohort list, metrics, operator action log, cohort defaults and broadcast-mode chip, and
gets a `lastUpdated` stamp it never earned, so the health strip captions all of it as fresh. The
broadcast-mode chip in particular is a claim about whether this service can move money, and
`SESSION_EXPIRED` still promises the operator that "Monitoring rebuilds from this service's state
after you sign in".

The new spec block 05-32 wrote is thorough about everything it covers, including two genuine
anti-vacuity controls. It has no ABA row, which is exactly why this passed green.

## The rule this plan holds

**A guard discards an answer by comparing what the answer is ABOUT, and a status is not an identity.
A list read is a fact about one SESSION, so the thing captured before the await and compared after it
must identify that session, not merely report that some session exists.**

## Why the counter is bumped on END as well as on START

The correctness argument only needs the START bump: if every path that makes a session live takes a
fresh round, then session B always holds a different round from session A and the ABA case is closed
whatever happened in between.

The END bump is what makes the field mean what its name says. Without it a round identifies "at most
one live session at a time"; with it a round identifies exactly one session, live or ended, and an
ended round is retired the instant it ends. That distinction costs one assignment in each of two
paths that already write a dozen fields, and it removes a class of future reasoning error in which
somebody adds a guard that compares a round without also checking the status. Both bumps are
therefore required, and the rows below cover each independently so neither can be dropped silently.

### What would have caught this and did not

Round 4 wrote seven rows for this guard, and every one of them is load-bearing about the case it

The general lesson, worth carrying past this phase: when a guard's subject is a state a system can
return to, the missing test is the one that RETURNS to it. A row that ends in a different state from
where it started cannot tell an identity comparison from an equality comparison on a label, and the
comment above the guard will keep claiming the stronger of the two.

There is a second lesson about comments. Round 4's comment described the guard the reviewer wanted,
and the code implemented something weaker; the comment then read as evidence that the stronger thing
was done. A comment that states an invariant is a claim, and it needs a row the same way the code
does.
