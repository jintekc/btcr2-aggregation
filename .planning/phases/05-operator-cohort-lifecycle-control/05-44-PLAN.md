## The defects, stated precisely

### IN-17: a repair instruction printed to an operator with no console

The settings routes are registered inside the operator-auth block in
`packages/service/src/hono-adapter.ts` (the gate at `:828`, the settings routes at `:903`), and
`operatorAuth` is constructed in `packages/service/src/index.ts:694` only when an operator password is
configured. So a service booted with no `OPERATOR_PASSWORD`, which is the documented fail-closed
posture (D-07), has no `GET` or `PUT /v1/operator/settings` and no console to reach them from.

The refusal warnings are emitted by the holder either way. Both consequence clauses
(`packages/service/src/runtime-settings.ts:823-824` and `:839-841`) name the operator settings
surface as the repair available right now, so that boot prints an instruction to set the
participation terms in a surface the service did not mount. The environment half of each sentence is
still true, so the line is misleading rather than wrong, and the same boot already prints a loud
no-operator-password warning next to it. That is why this is info rather than a warning, and it is
still a false promise made by the one output an operator reads at the moment the refusal happens.

### IN-16: the fourth statement of one fact

`docs/DEPLOY.md:358`, in the participation-terms prose section, still reads that a boot value above
the cap is ignored and never truncated, and that until you shorten it the join flow has no terms step
at all. That is the WR-10 and IN-13 overclaim verbatim, and it contradicts the same section's own
opening sentence three paragraphs earlier, which already says the terms can be set at boot OR in the
settings surface at runtime. The two environment-table rows fourteen lines below were corrected by
round 7; this sentence was missed by a search that found the rows.

## The rule this plan holds

**A disclosure exists to make somebody act, so it may only name repairs that exist for the reader it
is printed to. And one fact gets one account everywhere it is stated, with the console caption as the
fixed point.**

## Why a seed key rather than a qualifier in the sentence

The review offers both. A qualifier ("in the operator settings surface, when this service has an
operator password set") keeps one sentence for two situations and makes the reader work out which one
they are in, at the moment they are reading boot output about something that just went wrong. The bit
is cheap: `createService` already computes the condition one line below the holder's construction, so
the fact is available where it is needed and needs no new environment variable, no new route, and no
change to the served snapshot.

The seed key defaults to the fail-closed reading: a caller that says nothing gets the clause with no
in-session promise. That direction is deliberate. A default that promises a surface makes every
directly-constructed holder claim one, which is exactly the class of unearned claim this finding is
about; and it makes the two shipped ordering rows state their own precondition, which is worth more
than the two-word diff it costs them.
