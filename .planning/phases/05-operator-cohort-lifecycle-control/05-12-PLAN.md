## Phase Goal

Sourced from ROADMAP.md Phase 5, extended by the folded scoping one-pager `.planning/scoping/external-signers.md`:

> The operator runs aggregation and manages a cohort's lifecycle, and, per the owner's decision to fold the three scoping one-pagers into this phase as build work, a participant can sign the registration transaction in their own wallet.

MVP slice framing: **As a** participant who does not want to paste a private key into a web app, **I want to** sign my registration transaction in my own wallet, **so that** my key stays where I keep it.

This is the second of the three SLIP-FIRST folded builds (D-22). It introduces requirement PART-06, minted at planning time following the LIVE-01 precedent.

<objective>
Split the registration transaction builder into a template and a signer, hand the template out as an unsigned PSBT, and accept a signed one back under validation strict enough that a tampered PSBT can never reach broadcast.

Purpose: the registration transaction is a plain Taproot key-spend, so it can support an external signer today, unlike the cohort co-signing round, which needs an upstream signer interface this consumer app cannot add. The round trip needs no new dependency: the transaction class already used to build this exact transaction IS a PSBT. The one subtlety that decides the whole validation design is that an externally-signed transaction has an IDENTICAL transaction id but DIFFERENT raw hex, because signing uses auxiliary randomness and the transaction id excludes witness data. So the validator compares the witness-free unsigned transaction bytes, never raw hex, and never asks for the transaction id before finalizing.

Output: the template split with behavior preserved for existing callers, an unsigned-PSBT export, a pure five-verdict validator, round-trip parity under test, and the two-step wallet panel with its ephemeral-session warning and its honest co-sign limit.

Slip tier (D-22): SLIP-FIRST. This is one of the three folded scoping one-pagers (05-11, 05-12 and 05-13); if the phase runs long it re-parks cleanly to Phase 6 or the next milestone, and no CORE-tier plan (05-01 through 05-07 and 05-10) depends on it.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| external wallet -> browser | A returned PSBT is untrusted input that will be broadcast if accepted. |
| pasted text -> browser storage | Pasted material must not outlive the tab session. |
| wallet path -> real-funds guard rails | A second signing path must not become a second broadcast path around the gates. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-12-01 | Tampering | a malicious or altered returned PSBT | high | mitigate | The app never signs on this path; its duty is the reverse. The returned PSBT is compared byte for byte against the witness-free unsigned bytes of the exact template this page created, so any altered input, output, amount, or data payload is rejected before broadcast is offered. |
| T-05-12-02 | Information Disclosure | pasted PSBT or key material persisted | high | mitigate | Every ephemeral value lives in store or component state only and is cleared on teardown; a repository grep for the three browser storage APIs over the touched files returns no matches, so the ephemeral warning is backed by fact. |
| T-05-12-03 | Tampering | bypassing the ADR 0010 real-funds gate via the wallet path | high | mitigate | The validated raw hex feeds the SAME broadcast call inside the SAME register path the browser flow uses, so the acknowledgment gate, the re-entrancy guard, and the funding check all fire identically. |
| T-05-12-04 | Denial of Service | a very large pasted blob | low | mitigate | The paste field is a bounded, internally scrolling text area and parsing is a pure local operation with no network or disk cost; an unparseable blob returns a verdict rather than throwing. |
| T-05-12-05 | Spoofing | success copy describing a transaction other than the signed one | medium | mitigate | The fee, the paid amount, and the destination address in the success line are all derived from the returned transaction itself rather than from remembered state, so the copy describes what the wallet actually signed. |
</threat_model>
