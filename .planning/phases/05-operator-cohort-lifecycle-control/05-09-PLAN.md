## Phase Goal

Sourced from ROADMAP.md Phase 5:

> The operator runs aggregation and manages a cohort's lifecycle (open -> close -> finalize) and pauses, cancels, or reconfigures advertising from the console, without restarting the process, removing the last hardwired, uncontrollable behavior.

MVP slice framing: **As a** self-hosting service operator, **I want to** fill my own cohort's remaining seats with test participants, **so that** I can rehearse the whole funding and co-signing path on my own service without recruiting a second person.

This closes the fourth item earlier phases parked to Phase 5 (was 03 D-33). It exists because the Phase 4 live UAT needed two humans for something one operator should have been able to rehearse alone.

## Artifacts this phase produces (Phase 5, cumulative - excludes these from drift verification)

See the cumulative list in `05-01-PLAN.md`. This plan creates: `packages/service/src/test-peers.ts` with `spawnTestPeers` and `TestPeerHandle`, the per-service test-peer DID set and its member badge in the monitor projection, route `POST /v1/operator/cohorts/:id/test-peers`, the drill-down add-test-peers action, `packages/service/tests/test-peers.spec.ts`, and the e2e leg `e2e:testpeers`.

<objective>
Let one operator rehearse their own service end to end by filling a cohort's remaining seats with in-process participants that are real participants, clearly labelled as the operator's own.

Purpose: the Phase 1 filler loop is genuinely gone and the `fillers` option that remains on the demo-server type is compile-compatibility residue with no machinery behind it, so this is not a resurrection of the booth-era auto-fill. It is an explicit, gated, per-cohort operator action. Nothing in the protocol distinguishes a test peer from any other participant, which is correct: they really are participants. The badge therefore comes from a per-service set of DIDs written at spawn time, exactly the way seated roster keys are scoped per `createService` call, and never from inferring anything off the wire.

Output: a bounded spawner with abort-driven teardown, member badging, a gated route, the drill-down action with its rung-2 ceremony, a unit spec, and a hermetic e2e leg.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous browser -> gated test-peer route | Only an authenticated operator may spawn participants into a cohort on this service. |
| spawned peer -> live chain | On a live cohort a spawned peer co-signs a real transaction, so the operator must be told before it happens. |
| peer lifetime -> process resources | Each peer holds a subscription, so its lifetime must be bounded by its cohort. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-09-01 | Elevation of Privilege | POST /v1/operator/cohorts/:id/test-peers | high | mitigate | Mounted inside the gated block after both prefix guards, id-shape-guarded before any lookup; the route-semantics matrix pins the anonymous 401. |
| T-05-09-02 | Denial of Service | unbounded peer spawning | high | mitigate | The count is capped at the cohort's remaining seats, which is inherently bounded by n, and a zero-seat cohort is refused with 409; every peer is stopped on cohort settle and on service stop, with a post-teardown count assertion in the spec. |
| T-05-09-03 | Information Disclosure | throwaway peer keys | medium | mitigate | Peer keys are created in-process, never returned by any route, never logged, and never written to disk; only the peer's DID crosses into the badge set. |
| T-05-09-04 | Repudiation | live peers co-signing real transactions | medium | mitigate | The live-mode confirm line states before the action that peers co-sign for real and their DIDs are anchored on the named network, and each spawn appends a server-stamped operator-action entry. |
| T-05-09-05 | Spoofing | test-peer badging | low | mitigate | The badge derives from a per-service DID set written at spawn time, never inferred from a protocol field, so a genuine external participant can never be mislabelled as the operator's own. |
</threat_model>
