## Phase Goal

Sourced from ROADMAP.md Phase 5:

> The operator runs aggregation and manages a cohort's lifecycle (open -> close -> finalize) and pauses, cancels, or reconfigures advertising from the console, without restarting the process, removing the last hardwired, uncontrollable behavior.

MVP slice framing: **As a** self-hosting service operator, **I want to** cancel a cohort from its drill-down and be told exactly what I am about to destroy, **so that** I never end a funded cohort or a room full of seated participants by accident.

This is the browser half of the cancel slice proven server-side in 05-01. It also lands `ConfirmPanel`, the confirmation primitive every later destructive action in this phase composes.

## Artifacts this phase produces (Phase 5, cumulative - excludes these from drift verification)

See the cumulative list in `05-01-PLAN.md`. This plan creates: `ConfirmPanel` (packages/web/src/ui/primitives.tsx), `packages/web/src/lib/lifecycle.ts` with `cancelAvailability` / `CancelAvailability` / `cancelRung` / `typeToConfirmMatches`, `LifecycleActions` (packages/web/src/components/operator/LifecycleActions.tsx), the `cancelCohort` client and store action, and the `canceled` member of `ChipKey`.

<objective>
Give the operator the Cancel action on the cohort drill-down, wrapped in the laddered confirmation ceremony the UI-SPEC fixes, and render the canceled fate in the console list.

Purpose: the server can already cancel honestly (05-01). What is missing is the human boundary: a destructive act must name its real consequences, and the top rung (a cohort whose beacon address already holds funds) must cost more than one click. Building `ConfirmPanel` here once means every later rung (finalize, dismissal, kill switch, test peers) composes it rather than re-inventing an inline confirm block.

Output: the `ConfirmPanel` primitive, pure availability and rung predicates under unit test, a `LifecycleActions` section on the drill-down, a `cancelCohort` client plus store action on the shared session-expiry path, and the `Canceled` chip wired into the Ended group.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator browser -> gated cancel route | The browser holds the session cookie; a cross-site page must not be able to drive this action. |
| server projection -> rendered console | Rendered fate and funding facts come from the served projection, never from optimistic client state. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-02-01 | Tampering | cross-site request to the cancel route | high | mitigate | The route already sits behind `requireSameOrigin()` on the whole `/v1/operator/*` prefix, layered on the `SameSite=Strict` session cookie; this plan adds no GET that mutates. |
| T-05-02-02 | Spoofing | rendered cohort fate | medium | mitigate | The Canceled chip is derived from the served `OperatorCohortDTO.state`, never set optimistically, so a failed cancel cannot make the console claim a cohort ended. |
| T-05-02-03 | Information Disclosure | rung-4 recovery-key disclosure | high | mitigate | The confirm renders only the recovery-key STATE (operator-held versus throwaway) carried by the funding view; the key value is never carried to the browser (the 04 T-04-06-04 pin). |
| T-05-02-04 | Elevation of Privilege | session expiry during a ceremony | medium | mitigate | A 401 on the action routes through the single `expireSession` path to an honest re-login rather than leaving a stale authenticated-looking surface. |
</threat_model>
