## Gap source

This plan closes **audit defects 4 and 8** from `.planning/phases/05-operator-cohort-lifecycle-control/05-AUDIT.md` (entries 4 and 6, HIGH honesty; entry 10, LOW coverage), filed as `.planning/todos/pending/2026-07-29-make-dismissing-an-ended-cohort-actually-dismiss-it.md` and `.planning/todos/pending/2026-07-29-make-the-type-to-confirm-gate-load-bearing.md`.

They are planned together because they are the same class of problem on the same surface: a confirmation ceremony that promises something the code does not deliver. The dismissal confirm promises an irreversible removal that does nothing observable; the rung-4 confirm is guarded by seven assertions against a function nothing renders. The dismissal confirm is itself rendered by the very `ConfirmPanel` whose gate defect 8 concerns, so one executor holds both coherently.

The dismissal defect was found INDEPENDENTLY by two agents (`honesty` and `coherence`) and confirmed by both skeptics.

**Read the skeptics, not only the finder.** Three corrections change the scope:

1. **The `failed` case does not exist.** The finder said the defect affects canceled, expired AND failed rows. Both skeptics established that `groupForChip` buckets a `failed` chip into the Needs attention group, where no Dismiss button renders at all. Do not write code or tests for it.
2. **The two live sub-cases behave differently and both must be covered.** A CANCELED cohort holds both records, so the DELETE returns 200 and the row simply comes back. An EXPIRED cohort whose monitoring ended record is absent (the app-side window-expiry path, where `runner.stopCohort` is silent and emits no runner event) makes the DELETE return 404, so the operator sees the shared action-failed line AND the row persists. A fix that only handles the first leaves the second worse than before.
3. **Something real IS destroyed today, just not what the copy promises.** The drill-down activity ring and the retained funding view go, and for a canceled row the "Canceled by the operator at" stamp degrades to the served reason. So this is not a pure no-op; it is a partial action behind a total promise.

**A consequence the audit did NOT name, and the fix turns on it.** The `terminal` map has TWO readers, not one. `listCohorts` renders the row, and `cohortFate` is a single expression over the same map (`terminal.get(cohortId)?.fate === 'canceled'`) served ANONYMOUSLY by `GET /v1/cohort-fate/:id`. That route is the one bit of out-of-band honesty a canceled participant gets: locked decision D-02 exists because the aggregation protocol has no message type that can carry an operator's cancel to a seated participant, so without it they read only "the cohort is gone" with no reason. A `forgetTerminal` that simply deletes the record therefore closes an operator-console honesty defect by switching OFF a participant-facing honesty feature, and no shipped spec sees it: `packages/service/tests/cohort-fate.spec.ts` pins the canceled bit after a cancel and a settle, never after a dismissal, and the rows this plan adds to `lifecycle-routes.spec.ts` only re-read `listCohorts()`.

So the dismissal removes the RECORD, not the FACT. `forgetTerminal` carries a canceled fate into a bounded, id-only carry set before deleting, and `cohortFate` reads that carry beside the map. Two shapes were offered for this (write the carry in `rememberTerminal`'s canceled branch, or leave a fate-only stub the list skips); this plan takes a third that is strictly narrower than both, and the reason is recorded in Task 1's action: writing the carry only in `forgetTerminal` leaves the eviction semantics of the non-dismissal path byte-identical (so the existing eviction and non-oracle rows keep their exact meaning), and it leaves `readvertiseExpired` untouched, so a re-advertised canceled cohort's old id still reads false rather than gaining a new permanent bit. A fate-only stub was rejected outright: it would put a config-less record into the map that `readvertiseExpired` would find and try to re-advertise.

**A consequence the audit noted that this plan must answer.** For an expired row, `readvertiseExpired` is the ONLY code path that deletes a terminal record, and it is the row's escape hatch. Once dismissal also deletes that record, dismissing an expired cohort destroys the ability to re-advertise it. The existing copy's "there is no undo" covers it only in the abstract, so this plan adds one sentence to the confirm for rows that offer Re-advertise. That is a deliberate, additive deviation from the fixed contract copy in `05-UI-SPEC.md`: the shipped sentence is kept verbatim so its existing pin stays green, and the new sentence is a separate exported constant rendered conditionally.

**On defect 8, read Skeptic 1's narrowing.** There is NO current misbehavior: the inline comparison and the predicate agree on every value the app can pass, because the single call site always passes an eight-character cohort-id prefix. The only divergence is an empty or whitespace expected value, where the inline expression arms immediately and the predicate never does, and that is unreachable today. What is genuinely broken is that the gate which ships has zero coverage while a spec claims to pin it, and that `05-02-PLAN.md` explicitly required the component to call the predicate. Fix it as a coverage and duplication defect, not as a live bug, and do not overstate it in the SUMMARY.
