## The defects, stated precisely

### WR-13: the sweep guards one branch of five

05-40 lifted the session-identity rule into one trio and applied it at fifteen call sites. At the
four gated reads (`refreshCohorts:1161`, `pollDetail:1679`, `loadSettings:1543`, `saveSettings:1567`)
the comparison sits AHEAD of every branch that writes, so all of them honor it. At the eleven gated
action verbs it sits inside the `unauthorized` branch only:

- `runAdvertisingToggle:901` (both `pauseAdvertising` and `resumeAdvertising`), `saveDraftEdit:1219`,
  `advertise:1253`, `readvertise:1307`, `discard:1342`, `exportCohort:1360`, `cancelCohort:1374`,
  `finalizeCohort:1401`, `addTestPeers:1429`, `disableBroadcast:1465`, `dismissEnded:1489`.

Every other branch (`ok`, `refused`, `declined`, `unreachable`, and the `catch` in `saveDraftEdit`)
writes unconditionally. The trio's own docstring states the rule without qualification: "an answer is
evidence about the session that ASKED, never about whichever session happens to be live when it
lands." Eleven verbs follow it for one answer in five.

The reviewer reproduced the harm against the shipped store, no source modified: session B had opened
`B-COHORT`; session A's advertise landed afterwards, wrote A's green confirmation into
`advertiseMessage`, re-read the list, and then navigated B into A's freshly minted cohort. The last
hop is the file's one remaining status-as-identity comparison, guarding `openCohort` at `:1290`,
which is exactly the comparison `sessionRound` exists to replace, left in the one place the round did
not reach. The second half of the same repro is the failure direction: session A's cancel came back
500 and painted the bad-tone action-error sentence into a console that canceled nothing.

The window is one click plus one round trip with a session boundary inside it, which is narrower than
the read paths WR-08 was filed about. It is not cosmetic: the navigation persists until the operator
navigates back, and the wrong bad-tone sentence tells them an action they never took did not go
through.

### IN-18: one shared array in every reset

`GATED_SLICE_RESET` (`:786-826`) is spread, so its top-level keys are copied, but its four nested
values (`cohorts: []`, `rows: []`, `operatorActions: []`, `view: { kind: 'list' }`) are the SAME
objects on every `signOut` and every `expireSession`, and they land in live store state. Nothing
mutates them today; the reviewer checked for `sort`, `reverse`, `splice` and `push` against a store
array across `packages/web/src/components/operator/*` and `lib/operator-rows.ts` and found none. The
hazard is that the first in-place mutation anywhere, an in-place sort of `rows` in a future list
surface being the obvious one, would corrupt the constant itself, and every later reset would carry
the corruption, with the bug appearing in a session that never ran the mutating code.

## The rule this plan holds

**An answer is evidence about the session that asked, on every branch, without exception. A status
is not an identity anywhere in this file. And ending a session hands the next one fresh containers,
never the previous one's.**

## Why the guard sits after the 401 branch and not before it

The same ordering the four gated reads already use, and for the reason `refreshCohorts` records at
`:1110-1123`: a 401 is session-scoped and must be acted on by whichever call discovers it, so its own
comparison lives inside `expireIfStillAsking` rather than behind a guard that returns early. Below
that branch nothing is evidence about the session that is live now, so one comparison covers the
rest.

Two verbs need a SECOND read of the comparison rather than a cached boolean, and this is the one
trap in the plan: `advertise` and the advertising toggle both `await get().refreshCohorts(baseUrl)`
inside their success branch. A session can end inside that await (the refresh itself can 401), so the
value captured before it is stale by the time `openCohort` runs. `saveSettings:1567` reads the
comparison ONCE because no await intervenes between its branches; `advertise` must re-read it after
the refresh. Caching one boolean across that await would reintroduce the same class of bug in a new
place.
