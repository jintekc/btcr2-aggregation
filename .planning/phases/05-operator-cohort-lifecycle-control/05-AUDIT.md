### 1. [HIGH] Anonymous POST /v1/terms/acceptance grows the artifact store without any bound, rate limit, or dedup

- Found by: `auth-gating`
- Location: `packages/service/src/hono-adapter.ts:722`
- Skeptic severity assessments: n/a, n/a

**Claim.** The one anonymous mutating route this phase added writes an unbounded number of distinct records into the process-wide artifact store, with no per-caller throttle, no per-DID cap, and no cap on the store itself, so an unauthenticated remote caller can drive the single-box coordinator to memory exhaustion.

**Failure scenario.** Operator self-hosts with TERMS_TEXT set (the documented way to turn on the feature; demo-server.ts:432 seeds it, demo-server.ts:292 wires a MemoryArtifactStore). An attacker generates ONE k1 did:btcr2 keypair locally - no registration, no cohort, no session needed, exactly as the browser participant flow does - then loops: build {'@context','type',serviceDid,cohortId,termsHash,participantDid,acceptedAt} with acceptedAt incremented by 1 ms each iteration, schnorr-sign termsAcceptanceSigningBytes, POST to /v1/terms/acceptance. Every request passes all six checks in recordTermsAcceptance (cohortId existence is deliberately NOT checked, per the docstring), so every request reaches `await putAcceptance(store, hash, record)` at hono-adapter.ts:347. Each differing acceptedAt yields a different canonical hash, so MemoryArtifactStore.put (store.ts:98) inserts a NEW Map entry every time rather than overwriting. Nothing ever deletes an acceptance (ArtifactStore has no delete). At a few thousand requests/second the coordinator's heap grows until the process OOMs, taking down the API, the SPA, and every in-flight cohort with it (single coordinator process, ADR 0014). With a FileSystemArtifactStore it is a disk-fill instead.

**Evidence.** hono-adapter.ts:722-746 registers the route with only `bodyLimit({maxSize: 16*1024})` and a try/catch; there is no throttle. The only throttle in the service is `createLoginThrottle` (operator-auth.ts:119), wired solely to loginHandler (index.ts:682). recordTermsAcceptance (hono-adapter.ts:256-349) ends unconditionally with `const hash = termsAcceptanceHashHex(record); await putAcceptance(store, hash, record);`. `acceptedAt` is validated only by `if (Number.isNaN(Date.parse(record.acceptedAt)))` (line 316) and a 512-char length bound, so it is effectively free entropy. index.ts:623 documents that `resolveBtcr2SenderPk` decodes a k1 DID's key directly from the DID string, so no service-side registration is required for the signature to verify. The 05-13 SUMMARY (line 194) shows the phase reasoned about store growth only on the REFUSAL paths (T-05-13-04: "each refusal path is also a potential store-growth path"); the success path was never bounded. Contrast the repo's own discipline elsewhere: MAX_TERMINAL = 24 in operator-cohorts.ts:712 with an explicit T-06-02 DoS rationale, MAX_TEST_PEER_DIDS = 200 in test-peers.ts:62, and the bounded operator-actions ring in monitor.ts.

#### Skeptic 1 (refuted=false, confidence=high)

I read every file on the path and tried five refutation angles; all failed.

1) Route reachability. packages/service/src/hono-adapter.ts:722 registers `app.post('/v1/terms/acceptance', bodyLimit({maxSize: 16*1024, ...}), handler)` in the PUBLIC block, before and outside the `if (operatorAuth)` block. The only `app.use(...)` middlewares in the whole adapter are `requireSameOrigin()` and `requireOperator()`, both scoped to `/v1/operator/*` (lines 757, 765), so nothing guards this route. Grepping throttle/rateLimit across packages/service/src finds only `createLoginThrottle` (operator-auth.ts:122), wired solely into `loginHandler` at index.ts:683. demo-server.ts adds no middleware either.

2) Precondition. The handler passes `termsText: runtimeSettings?.termsText.value`, seeded from `process.env.TERMS_TEXT` (demo-server.ts:432, threaded at 524), and `store` is a MemoryArtifactStore (demo-server.ts:292). `serviceDid` and `resolveSenderPk` are always wired (index.ts:1333/1338). With the feature enabled (its intended state) all four dep guards pass.

3) Signature is not a barrier. `resolveSenderPk` is the library's `resolveBtcr2SenderPk`; the shipped implementation at packages/service/node_modules/@did-btcr2/method/dist/esm/core/did-sender-resolver.js:71-90 returns `new CompressedSecp256k1PublicKey(components.genesisBytes)` for `idType === 'KEY'`, decoded straight from the DID string. No registration, no cohort, no session: an attacker with one locally generated k1 keypair signs valid records offline.

4) No dedup, no cap. recordTermsAcceptance ends unconditionally with `const hash = termsAcceptanceHashHex(record); await putAcceptance(store, hash, record);` (hono-adapter.ts:346-347). putAcceptance (store.ts:231) is a bare `store.put('acceptance', ...)`; MemoryArtifactStore.put (store.ts:96) is `this.#map(kind).set(normalizeHexKey(hashHex), value)`. termsAcceptanceHashHex is JCS-canonicalize -> sha256 over the whole record (packages/shared/src/tos.ts:176), so any differing field yields a NEW Map key rather than an overwrite. The ArtifactStore interface (store.ts:69-80) declares only put/get/has/entries: no delete, no eviction, no size bound anywhere.

5) Entropy is genuinely free. `acceptedAt` is checked only by `Number.isNaN(Date.parse(...))` (line 316) plus the 512-char MAX_ACCEPTANCE_FIELD_LEN; `cohortId` is free within /^[0-9a-zA-Z-]{1,64}$/; cohort existence is deliberately NOT checked (documented at lines 250-253 as an anti-enumeration choice). An unbounded set of distinct, fully valid records therefore exists.

The phase's own docstring confirms the exact gap: "nothing reaches the store until every check below has passed, so an anonymous caller cannot grow this service's store by failing (T-05-13-04)" - growth by SUCCEEDING was never bounded. Contrast MAX_TERMINAL = 24 (operator-cohorts.ts) and MAX_TEST_PEER_DIDS = 200 (test-peers.ts) in the same phase.

**Correction.** The defect is real and the mechanism is stated correctly. Three refinements: (a) the trigger is narrower than the title implies - the route is mounted unconditionally, but with no terms configured it refuses at the first dep guard ("this service has no participation terms set") before any store write, so only services that actually set TERMS_TEXT (or set terms via the operator settings patch) are exposed; (b) the disk-fill variant is hypothetical in this repo - FileSystemArtifactStore is exported at index.ts:188 but nothing in packages/ or e2e/ wires it at boot (demo-server.ts:292 always constructs a MemoryArtifactStore), so the shipped failure mode is heap growth only; (c) per-record cost is sub-KB (seven strings, each <=512 chars), so heap exhaustion needs on the order of millions of accepted requests, and the more immediate pressure at a few thousand requests/second is single-threaded CPU saturation from one schnorr verify plus JCS canonicalize plus two sha256 per request on the event loop, which starves in-flight cohorts before the OOM lands. Unbounded, unthrottled, un-deduped growth of a process-wide store from an anonymous route remains the accurate core of the finding.

#### Skeptic 2 (refuted=false, confidence=high)

I tried to refute this and could not: I reproduced the exact trigger in-process.

Code read (all current, /home/jintek/projects/github/@jintekc/btcr2-aggregation):

- `packages/service/src/demo-server.ts:292` wires `const store = new MemoryArtifactStore()` (the shipped entrypoint never uses FileSystemArtifactStore), and demo-server.ts:432 seeds `termsText` from `TERMS_TEXT`; docs/DEPLOY.md:307 and :454 document that as the way to enable the feature (also runtime-editable via the settings surface).

Reproduction (read-only, in-memory, no files written): built the exact wiring the shipped route uses (`createHonoApp` + `HttpServerTransport` + `resolveBtcr2SenderPk` + `createRuntimeSettings({termsText})` + `MemoryArtifactStore`), generated ONE fresh k1 identity that was never registered and never joined anything, and posted 300 acceptances naming a nonexistent cohort (`no-such-cohort-000`) with `acceptedAt` incremented by 1 ms. Result: `{ ok: 300, bad: 0, distinctStored: 300 }` - every request returned 200 and every one added a distinct store entry.

The only things I found that could soften it, neither of which refutes it: (1) the feature is opt-in (an operator with no TERMS_TEXT gets a 400 from the `!termsText` guard at line 275) - but the finding already states that and it is the documented way to run the feature; (2) docs/DEPLOY.md:368-380 advises an nginx `limit_req` of 10r/s - advisory, not shipped, scoped in prose to the tx proxy and `/cas/*`, and it caps the RATE, not the total: 10r/s still stores ~864k permanent records per day per IP, and distributed sources bypass it entirely. The growth is also permanent (nothing deletes), which distinguishes it from a transient CPU flood.

**Correction.** The defect is real as described; two details should be stated more precisely. (a) Throughput: my in-process loop sustained ~430 accepted writes/sec including client-side signing; the server-side per-request schnorr verify is the practical limiter, so "a few thousand requests/second" is optimistic. The claim does not depend on it - the store is unbounded at any rate, and the records are never evicted, so the growth is cumulative and permanent rather than transient. (b) Mitigating context worth noting alongside the finding: the route only exists in the enabled state when TERMS_TEXT (or the runtime terms setting) is non-empty, and docs/DEPLOY.md:368-380 already advises a proxy-level 10r/s throttle, which slows but does not bound the growth and does not name this route. Also worth adding: there is no dedup even for an identical (participantDid, cohortId) pair - only acceptedAt has to differ, and the participant store's own comment at packages/web/src/stores/participant.ts:1564 notes that "two acceptances differ only in their timestamp, so both would verify and both would be stored", which shows the duplicate-write property was observed client-side but never bounded server-side.

### 2. [HIGH] Broadcast kill switch does not stand down the funding stage, so the console keeps asking the operator to send real sats to a beacon the service will never spend

- Found by: `money-path`
- Location: `packages/service/src/index.ts:1112`
- Skeptic severity assessments: high, high

**Claim.** The per-cohort kill-switch predicate `cohortUsesLivePath` gates only the beacon-tx builder and the broadcaster, so a cohort advertised after the switch engages still starts a funding watch and still publishes a `waiting` funding view, prompting the operator (and any anonymous poller) to fund a beacon address whose UTXO the fixture path never reads or spends.

**Failure scenario.** Operator boots with LIVE=1 BROADCAST=1 (e.g. mainnet or mutinynet) and no RECOVERY_KEY (recoveryKeyState = 'throwaway'). They click `Disable broadcast`. They then advertise a new cohort (advertising is gated only on `paused`, never on `broadcastDisabled`, so this is the documented post-switch behavior: "New cohorts will be created on the fixture path"). Seats fill, `keygen-complete` fires, and `runner.on('keygen-complete', ...)` at index.ts:1112 starts `createFundingWatch` unconditionally (it is inside `if (opts.broadcast && live && netConfig)`, which is still true). Its first poll runs immediately, so `monitor.noteFunding` records `{ state: 'waiting' }`; `noteFunding` only checks `serviceMode !== 'live'` (monitor.ts:1425), and `serviceMode` is the cached BOOT mode, still `'live'`. The console now shows a `Needs funding` chip and the Funding card renders "Waiting for funds. Send at least N sats in one single payment from your own wallet, then this stage advances automatically." (FundingStage.tsx:56) plus the copy-able beacon address. Meanwhile `onProvideTxData` took `provideTxDataFixture`, so the cohort co-signs a dummy prevout, `signing-complete` fires, `releaseCohortTables` stops the watch, and `shouldBroadcast` returns false so nothing is published. The monitor's retained `fundingViews` entry is left at `state: 'waiting'` with `terminal: undefined`, so (a) the ended cohort's drill-down keeps rendering the same "send at least N sats" instruction forever, and (b) `publicFunding` (monitor.ts:1528-1539) keeps returning `awaitingFunding: true` on the anonymous `GET /v1/funding/:cohortId` for a cohort that already finished. An operator who acts on that prompt sends real bitcoin to an n-of-n MuSig2 beacon address that this service will never spend from; with the default throwaway recovery key the disclosure right beside it is literally true - "funds sent to this address are unrecoverable".

**Evidence.** index.ts:835-841 `cohortUsesLivePath` is consulted at exactly two places - `onProvideTxData` (index.ts:850-861) and `shouldBroadcast` (index.ts:987-996). index.ts:1112 `runner.on('keygen-complete', ({ cohortId, beaconAddress }) => { if (fundingWatches.has(cohortId)) return; ... createFundingWatch(...) })` has no kill-switch test. monitor.ts:1425 `if (serviceMode !== 'live') { return; }` is the only gate on `noteFunding`, and monitor.ts:1359 `const funding = serviceMode === 'live' ? fundingViews.get(cohortId) : undefined;` - `serviceMode` is `const mode: ServiceMode = broadcaster ? 'live' : ...` cached at index.ts:1030 and deliberately never re-derived. monitor.ts:1516-1538 `publicFunding` guards only `serviceMode`, a `canceled` chip, and `view.terminal !== undefined`; a fixture-path cohort that SUCCEEDS sets none of those. packages/service/tests/kill-switch.spec.ts covers only `cohortKeepsLiveWiring`, the holder's one-way property, the route and the health bit - there is no funding assertion in it.
