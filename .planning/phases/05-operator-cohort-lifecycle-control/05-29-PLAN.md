## What the defect actually is, and one correction to the review's own fix

`classifyEndpoint` refuses an unverified second marker BEFORE it tries to identify the observed
chain, and `checkEndpoint` only probes that second marker when block zero already matches ours. So
on any `ourNetwork` carrying a `distinguishingBlock`, an endpoint on a different chain family never
gets a second probe, arrives with no distinguishing marker, and is classified `unreachable`.
`mutinynet` is `DEFAULT_NETWORK` and carries one. The participant is therefore told "Couldn't reach
that endpoint." about a host that answered correctly, and is sent to debug their network instead of
their endpoint choice, while `mismatch`, one of the four messages PART-05 and SC 6 both name
explicitly, is unreachable on the project's own default network.

**The correction, which matters because it is the difference between fixing this and appearing to.**
`05-REVIEW.md`'s sketch gates the new branch on `theirName === null`. That does NOT close the
default-network case. `identifyChain` successfully NAMES mainnet, testnet3, testnet4 and regtest,
because each has a unique block zero and no `distinguishingBlock`, so `theirName` is non-null for
exactly the four families this gap is about, the sketch's branch is skipped, and control falls
through to the same marker guard that produced the bug. Verified by reading `identifyChain` against
`NETWORKS` on this checkout.

The condition that actually decides it is the GENESIS COMPARISON, which is also how
`05-VERIFICATION.md` states the missing item: a block zero that differs from ours is conclusive on
its own, and no second marker can rescue it. The marker is load-bearing only in the one case where
block zero is ambiguous, which is precisely the case where the observed genesis EQUALS ours.

## Why this is a diagnosis fix and not a safety change

The endpoint is refused today and is refused after this change. Nothing that is currently rejected
becomes accepted. What changes is which of two refusal messages the participant reads, and therefore
whether they go and check their host (wrong, wasteful) or pick a different endpoint (right). That is
why the plan carries an explicit row asserting no observation newly returns `ok`: a reordering that
accidentally widened acceptance would be a far worse defect than the one being fixed, and the suite
should say so rather than the plan promising it.
