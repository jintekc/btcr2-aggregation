## The defect, stated precisely

### IN-06: one number in the derived budget is still chosen, and justified against a case that is not the worst one

05-33 replaced the route's chosen 4 KiB body limit with a budget DERIVED from the terms cap at a
proven worst case of six bytes per UTF-16 code unit. Beside that derived term sits a fixed headroom
of 4096 bytes, whose docstring says the whole non-terms body measures 184 bytes today, "so this is
roughly twenty times what it needs".

Measured against the same worst-case encoding rule the multiplier itself is derived from, that is not
true, and the figure does not match the ordinary case either. Reproduced during planning against the
real patch shape, byte-exact:

| body | bytes |
|---|---|
| non-terms body, 200 character ASCII name | 369 |
| non-terms body, 200 character control-character name | 1369 |
| terms at the cap in ASCII, ASCII name | 20369 |
| terms at the cap in control characters, control-character name (the worst legal body) | 121369 |
| the shipped budget | 124096 |

So the headroom is roughly three times what it needs rather than twenty, and the budget clears the
worst legal body by 2727 bytes rather than by the margin the comment implies. Nothing is broken today.

What is worth closing is the coupling: raise the service-name cap past roughly 682 and the settings
save wedge re-opens through the NAME field, with the whole suite green. Two things make that silent.
The budget's headroom does not carry a name term at all, and the measurement block varies only the
TERMS encoding while re-typing the name cap as a local literal in the spec
(`packages/service/tests/runtime-settings.spec.ts:678`), so a source cap change does not move the
measurement that bounds it. `docs/DEPLOY.md:352` also now tells a self-hosting stranger that "that
character count is the only limit either path applies", which is a byte budget short of true.

### IN-08: an option documents itself as a constant with no edit surface

`CreateServiceOptions.serviceName` (`packages/service/src/index.ts:426-433`) says it is "a boot-time
constant" and "display text only (no edit surface, no markup)". Since Phase 5 D-16 the name is
runtime-editable behind the gated settings route, and after round 5 deleted the static
`createHonoApp` option this option's ONLY consumer is the holder seed at `index.ts:670`. It is a seed,
not a constant. Round 5 edited the lines immediately below it and left the neighbouring claim
contradicting shipped behavior, in a codebase whose stated convention is that these comments are the
contract, and directly above a block that already describes the other six seeds correctly.

## The rule this plan holds

**A limit that governs a field belongs to that field, derived once, from every field it has to carry.
A number that is chosen rather than derived is only correct until somebody changes something else,
and a test that re-types the value it is meant to be watching cannot tell you when that happens.**
