## The defect, stated precisely

05-31 made `textKnob` drop an over-long free-text seed rather than truncate it, and the reasoning is
right: a truncated participation-terms document is one participants would DID-sign in mutilated
form. What is not finished is the DISCLOSURE around the drop, and the terms are not an ordinary
display field. They are a gate.

With the terms dropped, `hono-adapter.ts:307` sees no terms and refuses every acceptance,
`GET /v1/config` omits the key, and the web join flow has no terms step at all. An operator who
deliberately configured a DID-signed acceptance requirement is now running a service that does not
require one. The only record of that is a single `console.warn` line at boot.

The console gives them nothing to notice it with, and it gives them a false fact besides. `textKnob`
returns undefined; `field()` sets both `value` and `envDefault` to that same undefined; `project()`
therefore computes `changed: false`; and `SourceCaption` renders `SOURCE_ENV_DEFAULT`
(`SettingsView.tsx:43-45,372-377`). The settings surface tells the operator that this service's
ENVIRONMENT DEFAULT for the participation terms is unset, when the environment set a hundred
thousand characters of terms.

That is the same class of dishonest caption the holder's own clamp comment already names as a defect
worth fixing: "The gated settings read served the over-ceiling number with `changed: false`, so the
console captioned as this service's `env default` a window the runner's own TTL would overrule." The
module diagnosed the pattern in one field and then reproduced it in another.

## The rule this plan holds

**A caption is a fact the service reported. When this service REFUSED something the environment
supplied, refusing quietly and then captioning the absence as the environment's own choice is not a
smaller lie than getting the value wrong; it is a larger one, because it removes the operator's
reason to look.**

## Two decisions taken on the record

**The numeric seeds do NOT join this disclosure in this round.** The review permits either. The
stakes differ and the difference is the argument: a malformed `DEFAULT_SIZE` falls back to a value
the operator can SEE rendered on the same screen and correct in the same form, whereas a dropped
`TERMS_TEXT` falls back to an ABSENCE the operator cannot distinguish from never having set one, and
that absence turns an enforcement control off. There is also a mechanical reason: `numericKnob` is
called for `PORT` and for the runner knobs, which are not settings and have no place in a settings
DTO, so threading a collector through it would either leak non-settings variables onto this surface
or need a second parameter to suppress them. Recorded as a carried item for a future round, and
pinned as a prohibition so it is a decision rather than an omission.

**A dropped seed is NOT recorded in the operator-actions log.** The review offers that as a fallback
if the snapshot route is not taken. It is not taken here because that ring is scoped to actions an
operator took during a session and `signOut` clears it, so a pre-session boot fact filed there would
be misattributed to whoever signed in first and then lost at their sign-out. The served snapshot is
read on every visit to the settings surface and survives every sign-out, which is what a boot fact
needs.

## Two mechanical traps the executor will hit

Both are named here because each fails at compile time in a place that does not obviously belong to
this change.

`SETTING_LABELS` at `packages/service/src/hono-adapter.ts:150` is typed
`Record<keyof SettingsSnapshot, string>`. Adding a key to `SettingsSnapshot` therefore breaks that
declaration, and `recordSettingsChanges` at line 180 casts its loop key to `keyof SettingsSnapshot`
and then reads `.value` off it, which the new key does not have. The narrow fix is to give the seven
value-carrying keys their own exported type in `runtime-settings.ts` and to key both the label record
and the loop on THAT, which also states the distinction the new key introduces: seven of these are
settings and one is boot provenance.

`packages/service/tests/lifecycle-routes.spec.ts:553-575` asserts the served key set with an exact
sorted equality. That row must gain the new key. It is a reshape rather than a loosening: the
exact-equality discipline is the point of the row and it stays.

### What would have caught this and did not

The module that carries this defect had already DIAGNOSED it. The clamp comment 05-30 wrote says, in
so many words, that serving a value with `changed: false` made the console caption as this service's
environment default something the environment had not chosen. 05-31 then introduced a second field
with exactly that shape and did not check the caption it produced, because the round was about the
BOOT (does the seed wedge later saves) and the caption is a RENDER.

The general lesson, worth carrying past this phase: when a fix changes what a service STORES, the
next question is what the surface that renders the stored value now says. A field whose value became
undefined for a new reason renders identically to one that was always undefined, and no test of the
storage can tell those apart.

The second lesson is about the shape of a fallback. Dropping is the right choice here and 05-31 was
right to choose it, but a fallback that turns an enforcement control off is not the same kind of
event as a fallback to a default value, and it needs a disclosure sized to that difference rather
than the one the neighbouring field already had.
