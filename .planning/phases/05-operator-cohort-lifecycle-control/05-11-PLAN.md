## Phase Goal

Sourced from ROADMAP.md Phase 5, extended by the folded scoping one-pager `.planning/scoping/participant-esplora-override.md`:

> The operator runs aggregation and manages a cohort's lifecycle, and, per the owner's decision to fold the three scoping one-pagers into this phase as build work, a participant can supply their own chain-read endpoint.

MVP slice framing: **As a** participant who does not want to take the operator's word for what the chain says, **I want to** point my browser at my own esplora endpoint, **so that** I can verify UTXOs and confirmations against a source I chose.

This is the first of the three SLIP-FIRST folded builds (D-22). It introduces requirement PART-05, minted at planning time following the LIVE-01 precedent.

## Artifacts this phase produces (Phase 5, cumulative - excludes these from drift verification)

See the cumulative list in `05-01-PLAN.md`. This plan creates: per-network genesis block hashes in `packages/shared/src/networks.ts`, `packages/web/src/lib/esplora.ts` with `probeChain` and the endpoint classifier, the `ChainEndpoint` parameter on `packages/web/src/lib/tx-client.ts`, `ChainEndpointPanel` (packages/web/src/components/cohort/ChainEndpointPanel.tsx), `packages/web/tests/tx-client.spec.ts`, and requirement id `PART-05`.

<objective>
Let a participant choose their own chain-truth source, without weakening a single guard rail and without ever silently deciding for them.

Purpose: today every chain read and broadcast goes through the coordinator's same-origin proxy, so a participant must fully trust the operator's chain view. The proxy exists for good reasons and stays the zero-config default, so this is an addition, not a replacement. Two constraints shape the whole design. First, the endpoint must be a PARAMETER on the single existing register and broadcast path, never a second flow, because the ADR 0010 real-funds gate, the re-entrancy guard, and the funding check all live at the top of that one path and a parallel flow is how they get bypassed. Second, a browser cannot reliably distinguish a cross-origin rejection from a DNS failure at the JavaScript level, so classification comes from ordering the genesis-hash probe first rather than from parsing an opaque error message.

Output: per-network genesis hashes in the shared registry, an endpoint probe with a four-way classification, a parameterized chain client, the store threading, and the `Chain endpoint` disclosure with every documented state.

Slip tier (D-22): SLIP-FIRST. This is one of the three folded scoping one-pagers (05-11, 05-12 and 05-13); if the phase runs long it re-parks cleanly to Phase 6 or the next milestone, and no CORE-tier plan (05-01 through 05-07 and 05-10) depends on it.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| participant browser -> third-party esplora endpoint | A participant-chosen host now receives requests directly from the browser. |
| endpoint verdict -> real-funds guard rails | An override must never become a path around an acknowledgment gate. |
| endpoint response -> participant's chain truth | A wrong-chain endpoint would give the participant confidently false answers. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-11-01 | Information Disclosure | server-side request forgery via the endpoint | medium | mitigate | The fetch happens in the BROWSER, never on the server, so this is not server-side request forgery; the endpoint is never proxied through the service. The scheme is validated as https before any request, rejecting other schemes with the malformed message. |
| T-05-11-02 | Tampering | bypassing the ADR 0010 real-funds gate | high | mitigate | The endpoint is threaded as a parameter into the single existing register and broadcast call sites; there is no second flow. Gate parity is asserted by running the same scenario with and without an endpoint. |
| T-05-11-03 | Spoofing | a wrong-chain endpoint answering confidently | high | mitigate | The genesis-hash probe runs BEFORE any UTXO read and refuses a mismatched chain with both chain names in the message; the hashes live in the shared network registry, never as literals in the browser package. |
| T-05-11-04 | Denial of Service | repeated probing of a dead endpoint | low | mitigate | The verdict is cached per endpoint so the probe does not re-run on every read, and a failure stops the operation rather than looping. |
| T-05-11-05 | Repudiation | a silently swallowed broadcast | high | mitigate | Broadcast through the endpoint is a second explicit opt-in, off by default, and a failure reports its specific verdict rather than silently rerouting, so a participant always knows which path their transaction took. |
</threat_model>
